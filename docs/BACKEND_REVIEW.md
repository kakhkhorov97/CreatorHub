# CreatorHub backend review — 27 September 2026

The requested ER changes are implemented in the existing NestJS GraphQL/Mongoose structure. Model, validation, authorization, service, resolver, and test changes were made together. The source has 17 collection schemas, 34 model references, and 46 explicit indexes. `ER_UPDATE.md` maps changes to files; `schema.graphql` is the generated API contract.

## Implemented behavior

- API requests produce terminal logs with generated request IDs, matched routes, status, duration, and GraphQL operation/error metadata. Response X-Request-ID correlates requests with logs. Logging excludes payloads, variables, headers, query strings, raw documents, response data, and error messages. Focused HTTP/Apollo tests cover credential omission and GraphQL errors returned with HTTP 200. A live read-only request confirmed the running backend emits the request-ID header. Logs currently use the NestJS console logger; persistent log storage and external monitoring are not configured.
- `users` holds account/profile state with USER/CREATOR/ADMIN and preferredLocale default en. Credentials belong to EMAIL or PHONE authIdentities; social identities have no local password. Hashes are private and remain generated by the existing scrypt helper.
- Normalized email/phone/provider identifiers are uniquely reserved, including retained revoked identities. User and first identity are created atomically. Phone/password registration is usable without SMS, with verifiedAt absent. Email login requires confirmation.
- Google, Telegram, and Kakao ID tokens are checked using their configured audience, trusted key endpoint, RS256 signature, issuer, subject, expiry, issued-at time, and a single-use nonce. Known subjects reuse their account. Unknown subjects require a display name for registration. No automatic email-based merging occurs.
- Account-specific linking requires a recently created authenticated session and new-method proof. Pending email does not count as usable. Unlinking is serialized, cannot remove the last usable method, and revokes that method's sessions/tokens. Revoked subjects remain reserved. Phone-password replacement requires another linked sign-in and revokes sessions.
- First valid creator-profile publication and USER-to-CREATOR promotion share a transaction. ADMIN is preserved. Hidden/deleted profiles retain their account role.
- Categories have one editable name. Likes/comments target portfolio projects; follows target creator profiles. Follow records are retained on unfollow and renewed with a new followedAt. Duplicate state requests create no extra event; comments deduplicate through their client UUID.
- Followers receive alerts only for first project publication. Likes/comments/follows notify the creator. Edits, unlike/unfollow, and archive/republish do not trigger follower alerts.
- Source actions and durable activity events commit together. The API's bounded worker uses leases, transactional notification batches/checkpoints, retry delays, and recipient/event uniqueness. Reads recheck public visibility. Unavailable targets return no activity details. Inquiry notifications retain the existing synchronous transaction rule.
- Existing private inquiry access, version checks, snapshots, message retry keys, account suspension/deletion, refresh rotation, and token expiry handling remain covered by integration tests.

## Verification

Formatting, lint, type checking, API build, batch build, and GraphQL schema export passed. All 48 tests passed: 32 real disposable MongoDB/GraphQL/CLI scenarios, ten local signed-token cases, and six inquiry boundary tests. All 12 documented GraphQL operations validate against the exported schema. Tests use an isolated replica set and mocked mail; they do not exercise real provider accounts or production adapters.

## Limits and setup still required

The frontend and external provider applications are separate work. Configure email delivery and the providers you enable; frontend authorization must validate browser-bound state, redirects, and PKCE/code exchange as appropriate. The starter accepts completed provider ID tokens rather than implementing frontend callbacks. Its nonce and request-rate stores are in memory, so one API process is the supported starter deployment; shared transient infrastructure is required before scaling. Restarting invalidates outstanding social challenges.

Activity delivery polls every five seconds and is in-app only. Operational alerting for repeatedly failing deliveries and production query-plan/load checks are not configured. Phone-only accounts have no automated lost-password recovery. Phone registration does not establish number ownership. Data retention/anonymization policy, media storage, real mail/social integrations, and production deployment were not completed in this update.

No existing database was migrated. Old credential fields, session/token references, category labels, and notification/event indexes need the explicit migration described in ER_UPDATE.md. Do not run db:setup on an old populated database and assume it performs that migration.

Naming correction: the authenticated-user decorator is @CurrentUser() and its variables are currentUser. Event records use performedById. Lint, type checking, API build, and all 48 tests passed after this correction.

Resolver organization: all GraphQL response classes now live in their corresponding libs/dto feature folders, including the five previously declared inside resolvers. Formatting check, lint, type checking, API build, and schema export passed for this relocation. The generated GraphQL contract is unchanged; only definition order changed, verified by comparing sorted schemas. The existing 48-test result above predates this cleanup; tests were not rerun for the relocation.
